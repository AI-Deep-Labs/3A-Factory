# Release Notes: 4.0.1 (Hotfix: Anti-Bypass Sub-Agent Orchestration)

**Release Date:** 2026-08-04

Bản phát hành 4.0.1 là một bản vá nóng (Hotfix) nhằm giải quyết triệt để hiện tượng "vượt rào" (Bypass) của Agent Project Manager, đảm bảo tính toàn vẹn cho kiến trúc Enterprise v4 (Sub-Agent Orchestration).

## Nguyên nhân gốc rễ (Root Cause)

Trong quá trình thực thi kiến trúc v4, người dùng phát hiện ra rằng Agent Project Manager (PM) không thèm gọi các Sub-agents (như `developer` hay `architect`), mà tự mình ôm đồm xử lý toàn bộ các tác vụ.

Nguyên nhân xuất phát từ 2 đặc tính của hệ thống:
1. **Bản tính tối ưu hóa của LLM:** Các LLM mạnh (như Claude 3.5 Sonnet, Gemini 1.5 Pro) có xu hướng tự tối ưu hóa. Khi thấy task nhỏ, chúng lập luận rằng việc đóng gói ngữ cảnh để gửi cho Sub-agent là "tốn thời gian và lãng phí token", nên chúng quyết định tự làm để đạt tốc độ phản hồi nhanh nhất.
2. **Global Tool Scope của IDE:** Các IDE (như Claude Code hay Gemini CLI) tự động nạp (auto-load) toàn bộ các file `SKILL.md` thành các "Tool" dùng chung (Global Tools). Vì vậy, PM Agent luôn "nhìn thấy" và có quyền gọi các tool thực thi như `develop` hay `qa`.

Hệ quả là nguyên tắc Zero Bias và Four-Eyes Principle bị phá vỡ. PM vừa viết code, vừa tự review code của chính mình.

## Giải pháp khắc phục

Chúng tôi đã triển khai kỹ thuật **Negative Prompting (Hard Gates)**:
- Bổ sung lệnh cấm tuyệt đối bằng chữ in hoa vào `AGENTS.md`: `CRITICAL AGENT OVERRIDE: PM MUST NEVER EXECUTE CHILD SKILLS DIRECTLY`.
- Bổ sung chuyên mục **CRITICAL ANTI-BYPASS RULES FOR PM** vào `.agents/skills/project-manager/SKILL.md`.

Luật mới ép buộc PM đóng vai trò Supervisor thuần túy. PM bị cấm tự viết code hay tự review, mà bắt buộc phải sử dụng `invoke_subagent`.

## Điểm hạn chế (Limitations)

- **Phụ thuộc vào Prompt Obedience (Độ tuân thủ của mô hình):** Giải pháp này dùng "luật bằng chữ" để cấm LLM, thay vì dùng "luật bằng code" để khóa tool. Do đó, nếu Context Window của LLM trở nên quá dài và bị loãng, có khả năng cực nhỏ LLM sẽ "quên" lệnh cấm này.
- **Vẫn tốn Context Tooling:** IDE vẫn nạp các kỹ năng `develop` vào Context của PM, gây tốn một lượng nhỏ token mô tả tool không cần thiết.

## Vì sao lại lựa chọn giải pháp này?

Giải pháp lý tưởng nhất về mặt kiến trúc là **Tool Scoping** (Cắt quyền truy cập Tool ở tầng mã nguồn), tức là cấu hình để PM chỉ được cấp duy nhất tool `invoke_subagent`, và hoàn toàn bị "mù" trước tool `develop`.

Tuy nhiên, 3A-Factory là một Framework chạy bên trên các nền tảng (Client) có sẵn như Claude Code hay Gemini CLI. Chúng ta **không thể can thiệp sửa mã nguồn lõi (Core Engine)** của các nền tảng này để chia quyền Tool. 

Vì vậy, chèn Hard Gates bằng Negative Prompting là giải pháp **thực dụng, khả thi nhất và là tiêu chuẩn ngành (Industry Standard)** hiện tại để ép LLM tuân thủ ranh giới vai trò trong môi trường Global Tools.
